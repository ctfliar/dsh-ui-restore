# 与团队任务板的可选集成

## 0. 结论先行

**本插件不依赖任何团队/任务板能力。** 插件只提供四个工具，产物是 run 目录里的文件；
谁来回合、谁派活、任务状态记在哪，都由使用者决定。

- 没有团队任务板：用 DeepSeek Harness 基线的 subagent + 五个预设，串行闭环即可跑完。
- 有团队任务板：可以并行多个页面、把轮次变成可审计的任务，但**插件本身一行代码都不改**。

## 1. 为什么不做硬依赖

1. **产物已经是契约**：截图、`diff.json`、`probe.json`、`report.md/html` 都在 run 目录里，
   任何编排方式只要会读文件就能接力，不需要插件知道调度器的存在。
2. **基线已经够用**：`dsh-tool-subagent` 的 `agentPreset` / `allowedAgentPresets` 就能固定
   「设计 / 画师 / 接线者 / 验收者」四个子角色（本插件的五个预设已经这样声明）。
3. **团队能力是第三方实现**：不同团队插件的包名、工具名、任务模型都不一样；
   写死任何一个包名，都会让没装它的用户在激活预设时直接失败。
4. **失败面可控**：任务板不可用时，降级成串行即可；硬依赖会把「可选增强」变成「装不上就废」。

因此：插件代码、`cordis.patch.yml`、SKILL 里都**不出现任何团队工具调用**；
团队集成的具体做法只写在本文档里。

## 2. 两种实现

### A. 基线串行（默认，零额外依赖）

```
用户 / 队长
  ├─ 建档案、定模式、准备 run 目录
  ├─ design.mode=from-scratch 时先派设计师（agent_preset=ui-restore-designer）→ 设计包
  ├─ subagent（agent_preset=ui-restore-painter）→ 实现 + 截图 + 规则门禁
  ├─ subagent（agent_preset=ui-restore-verifier）→ 探针 + 差异 + 判定
  │     └─ needs_revision → 回到画师（同一 run 目录）
  └─ 达标 → 验收者出报告 → 交付
```

- 交接靠**消息 + run 目录**：消息只给 run 目录、设计源、本轮变更（模板见 SKILL 第 7 节）。
- 轮次由队长数：`thresholds.maxRounds` 到顶就停。
- 优点：简单、可预测、任何 DSH 组合都能用。
- 缺点：多页面只能顺序做；会话结束就丢失「第几轮、谁在等谁」的上下文。

### B. 团队任务板（可选增强）

把「每轮的一次实现/验收」变成一条任务链，任务板负责顺序、状态与唤醒：

```
页面 A：draw(A,r1) → verify(A,r1) → [needs_revision] → draw(A,r2) → verify(A,r2) → report(A)
页面 B：draw(B,r1) → verify(B,r1) → report(B)        ← 与 A 并行
```

无参考自主设计（`design.mode=from-scratch`）时，前面多两条任务：`design(A)` → `review-design(A)`。
设计评审 `pass` 后才解锁 `draw(A,r1)`；验收任务用同一份设计包（`mock.png` + `ui-spec.json`）判定，
评审结论（`<run>/review/design-review.json`）也作为验收依据之一。

两种常见拆法，二选一：

| 拆法 | 任务粒度 | 适合 |
| --- | --- | --- |
| 按轮次拆 | 每轮一条实现任务 + 一条验收任务，验收依赖同轮实现 | 轮次多、需要逐轮审计 |
| 按阶段拆 | 一条「实现到达标」任务 + 一条「验收与报告」任务 | 轮次少（1~2 轮）、页面多 |

任务描述至少写清下面几项，缺一项就不要开工：

```text
页面：<页面名 / 路由>
档案：<档案 id 或 JSON 路径>
run：<runRoot>/<页面>-r<轮次>
设计源：image → <设计图路径> | mcp → <ui-spec 路径> | design → <run>/design/（mock.png + ui-spec.json） | none
设计评审：<run>/review/design-review.json（from-scratch 时必填，verdict 必须是 pass 才开工）
参考案例：<docs/knowledge/... 下的 passed / failed 案例路径（至多各 1 条）；无则写「无」>
范围：<允许改动的目录/文件>
上一轮结论：<findings 摘要或「首轮」>
完成判据：<合格线 / high 清零 / 规则命令通过>
```

**参考案例**由队长从项目知识库（`docs/knowledge/projects/<slug>/`）里挑，只给与本任务同类、
最近的一条 passed 与一条 failed；子角色按需读取（见 SKILL 第 2B 节），任务板不复制案例正文。
没有可用案例时写「无」，不要拿别的项目的案例凑数。

验收任务额外要求产出结构化结论（`verdict` + `findings[]`），并且**任务板只做调度，
不做判定**：判定属于验收者，任务状态只是它的投影。

## 3. 什么时候值得用任务板

值得：

- 同一批要还原 **3 个以上页面**，想并行；
- 还原周期跨天/跨会话，需要「哪一轮、谁在做、卡在哪」可查；
- 需要给非开发同学看进展（任务状态比聊天记录直观）；
- 团队本来就有一套任务板，且已经装好。

不值得：

- 单页面、1~2 轮就能过——串行更快；
- 环境受限（装不了团队插件，或权限不足）；
- 只是想让模型「看起来更忙」——任务板不会提高还原度。

## 4. 能力探测与降级

开工时看一眼会话里有没有任务板相关工具：

- 有 → 走 B，任务描述按第 2 节的字段填；每轮结束把结论写回任务。
- 没有 → 走 A，串行推进；不要在消息里假装有任务板。
- 用着用着失效（插件被禁用、权限变更）→ **降级到 A，不要中断**；run 目录与报告不受影响。

约定：任务板上记录的是**调度信息**（谁、哪轮、状态），验收证据仍然只认 run 目录里的文件。
任务状态写「完成」不等于验收通过；判定以 `report.md` 的 `verdict` 为准。

## 5. 为什么这套集成方式不会绑死

- 任务板换实现：只改任务创建/更新那几步，SKILL、预设、插件、档案都不用动。
- 从 A 切到 B：run 目录结构不变，历史产物照样能汇总成报告。
- 从 B 退回 A：把未完成任务当成普通待办继续做，产物仍在同一 run 目录续写。

一句话：**任务板是编排的可选加速器，文件与判定才是这个插件的地基。**
